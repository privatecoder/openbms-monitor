# OpenBMS Monitor

Cross-platform monitor for the Seplos BMS V2.0 (10C/10E, EMU1101). The monitor is read only unless maintenance functions are switched on (firmware view; parameters, serial numbers, clock, CAN protocol and calibration in the Parameters view). The separate `openbms-flash` CLI can write firmware only after its own validation and explicit confirmation. Beta (0.3.x), public repo; nothing is released to others yet, so code and APIs need no backward compatibility (user databases still change only by migrations, see below). Protocol knowledge comes from [seplos-emu1101-docs](https://github.com/privatecoder/seplos-emu1101-docs); the README describes features and the two buses.

## Layout

- `crates/openbms-proto`: frames, checksums, Seplos ASCII commands (telemetry 0x42, status 0x44, params 0x47 and writing them 0xA1, intra-pack 0x5A, serial numbers 0xA2/0xA4 and writing them 0xA3/0xA5, clock and history 0x4B/0x4D/0x4E, calibration 0xA0, CAN protocol 0xA6, pack control 0x45 and remaining capacity 0x49; the EMU1101-EXT identity and reads 0x64/03–06 in `maint.rs` and `remote.rs`), Modbus RTU (master system values, battery serial number), parameter decoding.
- `crates/openbms-transport`: serial and TCP transport (5 s connect timeout, write timeout).
- `crates/openbms-cli`: read-only command-line poller for debugging.
- `crates/openbms-flash`: standalone EMU1101 updater (probe, `.ehex` validation and dry-run, confirmed flash); the app's firmware view uses it as a library (`app/src-tauri/src/firmware.rs`).
- `app/src-tauri`: Tauri 2 backend. `lib.rs` holds connection (with its installation, `Link`), polling thread, watchdog and the monitor commands; `history.rs` the SQLite history (recording keyed per site = installation id, retention/compaction, series, export/import, site merge); `health.rs` the health report from it (per pack and day spread, rest, cycles, temperature; pair shares from raw rows; design `docs/superpowers/specs/2026-10-16-multi-write-health-alerts.md` part B); `installations.rs` what installations own (settings, the one-time move of old site keys, merge, archive, delete, overview, stored parameter states; design `docs/superpowers/specs/2026-10-14-installations-own-the-data.md`); `bundle.rs` / `installation_bundle.rs` / `maint_store/transfer.rs` an installation's ZIP: writing, checked unpacking, export, inspect and resumable import (plan `docs/superpowers/plans/2026-10-15-installation-zip.md`); `firmware.rs` firmware commands, progress events, flash guard, logs named and indexed per installation; `control.rs` pack control and the per-pack reservation every pack write takes; `notify.rs` the notification triggers from the poll thread's fresh answers (pure logic, tests) and `notifications.rs` their wiring and `tauri-plugin-notification` (design part C of the spec above); `maint.rs` / `maint_store.rs` the pack bus panel's backend and `maintenance.sqlite` (installations, boards, places, layout, diagnosis, parameter snapshots, log index, moves; live status, pack scan, master marker over the CAN socket, right-bank check, bootloader-pending records; design `docs/superpowers/specs/2026-10-13-simple-flash-flow.md`). `maint_store.rs` also keeps each installation's pack selection (`packs`: search / count / address), used from the next connection on.
  - `wiring.rs`: the installation setting "wiring" (how the inverter reaches the packs) and from it the bus rule every request passes. A connection binds its rule (`bind` → `Bound` guard, `unbind` on stop and MQTT take-over); changes for the bound installation are queued and applied by `settle`. Lock order everywhere: NOW → PENDING → BOUND.
  - `mqtt_source.rs` / `feed.rs`: the "Home Assistant (MQTT)" source, the Seplos add-on's OpenBMS feed from a broker instead of the RS485 bus (`docs/exchange/openbms-feed-v1.md`).
- `app/src`: React 19 + Tailwind 4 frontend.
  - `views/Firmware.tsx` and `firmware.ts`: firmware update view (behind maintenance functions) and its step logic; `views/PackBusPanel.tsx`, `maint.ts`, `maintStore.ts`: the one-screen pack bus panel (with the flash series, `flashSeries.ts`: several packs after one confirmation, slaves first, master last, stop at the first failure; the backend binds the confirmed list in `firmware.rs`), the chosen installation (sidebar, kept across starts; null = „Nur ansehen“) and the banner; `views/Installations.tsx`: the installations view; `views/InstallationTransfer.tsx`: its export and import.
  - `installData.ts`: the settings an installation owns (cell types, groups, pairs, diagnosis, notifications, devices, packs) through the backend, one cache for all components. Writes per key go through `settingWriter` (serialized, read back); `reloadSettings` reloads every scope loaded before, and a read started before a reload is dropped; a deleted installation is not retried. The old localStorage keys are handed to the backend once and removed after it reports them moved.
  - `locks.ts`: **the one place** that decides whether a field or action is shown, offered or locked, and why (`decideUi(action, facts)` → `{visible, locked, reason?, note?}`, `lockProps`, reasons as `lock.*` strings in `i18n.ts`). Components gather `UiFacts` and render the decision.
  - `connCheck.ts`: the connection form's checks (port, bus, broker settings, pack selection) before connecting.
  - `api.ts`: typed Tauri commands, plus a demo API (`isDemo`, data from `demo/capture.json`) used when running in a plain browser.
  - `views/`: Dashboard (overview, towers, pairs), PackDetail, Diagnosis, Parameters, History, Recording, Cells, CellAssign, GroupEditor, Sidebar.
  - `pairs.ts`, `diag/`, `cells/` (datasheet rules, pack and parameter checks), `params.ts`, `paramWrite.ts` (writing: raw values, the firmware's plausibility rules), `groups.ts`, `history/` (charts, client-side helpers), `notifications.ts` (notification settings and the wording handed to the backend; the block sits in Verlauf → Aufzeichnung). Nothing about a bank is kept in localStorage any more (only UI preferences like the connection fields and the chosen installation).
  - `i18n.ts`: all UI strings, German and English side by side.
  - `help.tsx`: info icons and help pages, rendered from `help/<lang>/<id>.md` (numbered and bullet lists styled apart; an internal link `[…](#<id>)` opens that page with its title).
  - `guides.tsx`: **the one place** that decides where a step-by-step guide appears (`GUIDE_PLACES`: guide → places) and the `GuideButton`; views only put `<GuideButton place="…"/>` (one guide at a place opens directly, several are offered to choose).
- `help/`: **generated**, do not edit. Source is `tools/gen_help.py` (topics, alarms), `tools/param_help.py` (parameters, switch bits) and `tools/guides.py` (the step-by-step guides `guide.*`: numbered steps, alternative cases as `cases`, one help target per step rendered as an internal link; a guide states order, decision and expected result and links the topics instead of copying them; its `topics` get it appended to their related links). The generator checks every related id and step target and refuses an id used twice. Access facts in help pages come from the catalog: `{ACCESS:<action>,…}` (own line in a body: a list of ways; in title/short and UI hints: one short line without versions or bit numbers, the same form as `accessText`), `{VIA:<action>,…}` (inline: „über die CAN-Buchse“, the ports of the ways the app uses), `{GATE:<group>.<bit>}` (inline: the actions whose ways need that switch bit, with their ports) and `{MIN}` are rendered by `tools/access_help.py` from `app/src/generated/access.json`, with the DE/EN names and templates in `app/src/i18n.access.json` (shared with `i18n.ts`). UI hints that restate a catalog fact end in `{{access}}` and are filled by `accessHint` (`access.ts`, list `ACCESS_HINTS`). After changing a route in `access.rs`: `UPDATE_ACCESS=1 cargo test -p openbms-proto the_ui_catalog_is_current`, then `python3 tools/gen_help.py`. Effects, sequences, wiring and the Group0 bit polarity stay hand-written prose.
- `data/cells/cells.json` + `data/schema/cells.schema.json`: bundled cell database; rules in `data/cells/README.md`.

## Commands

```sh
cd app
npx tsc --noEmit -p .          # type check
npm test                       # vitest
npx tauri dev                  # desktop app with hot reload
npm run dev                    # browser only, demo data
cargo test --workspace         # Rust tests (from repo root)
cargo clippy --workspace
python3 tools/gen_help.py      # regenerate help/ after editing the help tables
python3 -m unittest discover -s tools   # generator checks (placeholders, prose without bus claims)
```

`.github/workflows/ci.yml` runs the automated checks listed above, plus a frontend production build, on macOS for every push to `main` and every pull request (clippy with `-D warnings`), and fails when `python3 tools/gen_help.py` would change `help/` or `app/src/generated/`. Add a new check there when you add one here.

## Conventions

- Every user-visible string exists in German and English (`i18n.ts`, both help languages). German is the primary language of the user.
- Every value or feature that needs explaining gets a help topic in `gen_help.py` and an `InfoIcon` next to it. Help explains relationships and what to do, not only definitions.
- Content is generic: help texts, examples, code comments and test names never cite a particular installation (no dates, pack numbers or readings from someone's bank). Use neutral examples ("pack A / pack B, 40 mV at 10 A").
- No private files in the repo (own parameter exports, poll logs, recordings). Tests use synthetic data.
- Nothing personal in the repo, commits or release notes: no user or account names, no home-directory paths, no IP addresses of real gateways or brokers. Examples use documentation addresses (`192.0.2.x`) and neutral names.
- Language: answers to the user in German; code, comments, docs, commit messages and `CHANGELOG.md` in English (UI strings in both, see above).
- Work here may touch sibling repos (the Seplos MQTT add-on, the protocol docs, the knowledge base): they have their own rules. Ask before committing or pushing there, and stage only explicit paths, never the user's own uncommitted changes.
- No documentation of modified firmware here; that lives elsewhere.
- Patched firmware = **EMU1101-EXT** (Light 1.5.x, Full 1.6.x), identity 0x64/03 with signature `EXT`, format 05, 21 bytes. Supported: every original release, Light from 1.5.4, Full from 1.6.4, plus the one temporary build marked `TEMP(maint-1.6)` (first MAINT 1.6, `MNT` format 3; remove it with every `TEMP(maint-1.6)` mark once that board runs EXT). The authority for EXT capabilities is the firmware project's capability matrix (`mod/docs/firmware/uart-write-capabilities.md`) and its OpenBMS integration contract (`mod/docs/firmware/openbms-monitor.md`); functions follow each pack's reported image flags and read capabilities, never a version alone. New builds: one entry in `crates/openbms-flash/src/known.rs` (names as `ExtInfo::version` gives them).
- The accepted builds and the matrix stay compiled into the app (no remote list). **Before working on anything that touches EMU1101-EXT** (identity, flash acceptance, access/locks, help texts about ports or functions), fetch the current state from the public firmware repo `privatecoder/seplos-emu1101-docs` (branch `main`) and compare:
  - matrix: `mod/docs/firmware/uart-write-capabilities.md` against `crates/openbms-proto/src/access.rs`, `locks.ts` and the help (`tools/gen_help.py`, `tools/param_help.py`);
  - builds: `mod/firmware/releases/ext-light.json`, `ext-full.json` (current) and `references/ext-*.json` (earlier supported) against `PATCH_BUILDS` (`firmware_name` → `name`, `build_id`, `image_flags` → `flags`, `remote_capabilities` → `read_caps`, `ehex_sha256`, `app_sha256` → `code_sha256`, `info_hex` → base/patch);
  - e.g. `gh api repos/privatecoder/seplos-emu1101-docs/contents/<path> -H 'Accept: application/vnd.github.raw'`.
  On any difference (new or withdrawn build, other checksum, flag or capability, a function moved between buses), **report it to the user and ask how to proceed**; do not adopt it silently. If the repo cannot be reached, say so.
- Databases with user data change only by migrations (`app/src-tauri/src/migrate.rs`): numbered steps counted in `user_version` (`maintenance.sqlite`) or `meta.migration` (`history.sqlite`, whose `user_version` stays 1 so older builds do not move it aside), each in one transaction after a copy `<file>.bak-<n>`, idempotent, every row kept. SQL of a released step is frozen; changes are new steps. Only a file of an unknown layout is moved aside.
- Match the surrounding code: short comments that explain why, compact components, Tailwind tokens from `index.css` (`text-muted`, `bg-sunken`, `text-alarm`, …).
- Everything stored about a bank belongs to an installation id: the connection carries it (`connect(endpoint, installation)`), answers are stored only while that connection is current (`for_link`). „Nur ansehen“ stores nothing and writes nothing to a pack; the demo stays storage-free.
- Do not write ad-hoc `disabled={…}` / hidden rules in components: add or extend an action in `locks.ts` with a test in `locks.test.ts`, and give a locked control its reason as tooltip (`lockProps`).
- The pack selection (search / count / address) belongs to the installation (Anlagen → Anschlüsse); the sidebar shows the picker only for „Nur ansehen“, otherwise one line with the selection of the running and the next connection. An explicit count/address wins over the master's slave count.
- Checks that compare packs wait until every found pack has answered, so a partial picture right after connecting does not raise false warnings.
- Every user-visible change gets a line under `## Unreleased` in `CHANGELOG.md` (English, generic); a release renames that section to `## <version> — <date>` (version as in `Cargo.toml`, checked by `about.test.ts`); the release workflow takes that section as the release notes (`tools/release_notes.sh`).
- Updates: the release workflow signs the update packages with the updater key (secrets `TAURI_SIGNING_PRIVATE_KEY` / `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, public key in `tauri.conf.json`, `tauri.release.conf.json` switches the packages on) and writes `latest.json` in its own job; the app finds the newest release with one through the GitHub API (`updater.rs`). Without the private key, installed apps cannot be updated any more: never rotate it casually.
- Release: rename `## Unreleased` in `CHANGELOG.md`, set the version in the root `Cargo.toml`, `app/package.json` and `app/src-tauri/tauri.conf.json`, commit, tag `v<version>` and push the tag; `.github/workflows/release.yml` builds macOS (aarch64 dmg, app.tar.gz) and Windows (arm64/x64 setup) with signatures and `latest.json`. A broken release is fixed by a new version, never by moving a tag.
- Commit with explicit paths (`git commit -- <paths>`); unrelated local changes may be in the tree. Never print or commit the updater key.
- Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Pushing to `main` is routine.
