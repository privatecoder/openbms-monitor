# Maintenance build 1.1: identity query 0x64/03

Status: approved r4 (no Blocking/High in r4), 2026-10-13 (r1–r3 reviewed: `.orch/reviewer-codex-6-sol-maint-1-1-r1.md` … `-r3.md` in the knowledge base). Builds on `2026-10-12-maintenance-mode-design.md` (binding) and the implemented stage 1 + guided panel + installation picker. Superseded in parts by `2026-10-13-simple-flash-flow.md`: only the proto, dialog, catalog and display parts (points 1–3, 7) apply; the gating parts (sessions, blocks, `marker-foreign`/`maint-unknown` states, recovery row, persisted identity, post-flash expectations, points 4–6 and 8–10) are not implemented.

## Why

The maintenance build "16.06.13 MAINT" (now called 1.0) answers CID2 0x64 with two bytes `[marker flag, effective slaves]`. The app cannot tell from the device which image runs (0x51 reports only `16.06`), and a flag of 1 hides what the marker word in flash really contains.

MAINT 1.1 adds a read-only query `0x64` with `INFO=03` on UART1 (CAN socket bus), unicast to physical DIP address 0. It was flashed and measured on a bench board (all frames below are measured unless marked).

## Firmware facts (MAINT 1.1)

- Request `~20004664E00203FD30`. Answer RTN 00, 22 raw INFO bytes:

| Offset | Bytes | Content |
|---|---:|---|
| 0–2 | 3 | ASCII `MNT` |
| 3 | 1 | format version `01` (reject anything else) |
| 4–6 | 3 | base firmware major, minor, patch: `10 06 0D` = 16.06.13 (major/minor read at runtime from the stock constant used by 0x51; patch fixed in the image) |
| 7–8 | 2 | maintenance patch version major, minor: `01 01` |
| 9–12 | 4 | raw marker word from flash, little endian: `FFFFFFFF` off, `00000000` on, anything else unexplained |
| 13 | 1 | effective slave count (0 while the marker is active, after the next 1-s cycle) |
| 14–21 | 8 | build ID: first 8 bytes of the SHA-256 over the hooked app **with the fixed placeholder `MBID0000` in these 8 bytes**; the builder then writes the ID there. So it is not a prefix of the code hash. For this build `fe381985bfff8ad0` (not an authentication of the device) |

- `INFO=02`, start `01 C3 5A`, stop `00 C3 5A` keep their two-byte answers.
- start/stop accept only marker words `FFFFFFFF`/`00000000`; for any other word they answer RTN 05 and do not program or erase. A wrong token also gives RTN 05 without flash access (measured).
- Answers to `0x64/03` by image (measured): original firmware RTN 04; MAINT 1.0 RTN 05 without INFO (`~200046050000FDAF`); MAINT 1.1 RTN 00 with the 22 bytes.
- Code SHA-256 of the 1.1 image (decoded code, as `known.rs` hashes it): `734a4a4c73abbf991b2616b50958aff6c05cdcca93ebf3781867a179194e38f1`.

## Proposal

1. **Catalog.** `known::Release` gets an optional `build_id: Option<&'static str>`. `MAINT_BUILDS`:
   - "16.06.13 MAINT 1.1": code hash `734a4a4c…38f1`, build ID `fe381985bfff8ad0`;
   - the existing entry is renamed "16.06.13 MAINT 1.0" (same code hash `4d76a96f…f55d`, no build ID).
   The master-flash plan offers 1.1 as the maintenance build; 1.0 stays accepted. Both remain modified firmware (accepted like custom images, as today). Tests check both identifiers of 1.1 and the unchanged 1.0 hash.
2. **Proto.** `MaintInfo::request()` / `MaintInfo::parse(info)` for the 22-byte answer: base version (3 bytes), patch version (2), raw marker `u32` (LE), effective slaves, build ID `[u8; 8]`. Wrong signature, format or length → `Error::Layout`.
3. **Dialog (`openbms-flash::maint::dialog`).** Today `exchange` accepts RTN 00 only with two INFO bytes. New: an exchange bound to the request sent, with a typed result:
   - `03`: RTN 00 accepted only with exactly 22 bytes (`MaintInfo`); RTN 05 → `Rtn05`; RTN 04 → `Unknown0x64`; anything else (other length, echo, garbage) is filtered/ignored until the deadline → no answer.
   - `02`, start, stop: unchanged (two bytes).
   - `probe` becomes: `03` first; `Info(MaintInfo)` | after RTN 05: `02` → `Legacy(MaintStatus)` (MAINT 1.0 compatible) | RTN 04 → `No0x64` | no valid answer → `Failed`. A missing or malformed `03` answer is **never** reinterpreted as original or 1.0: it is `Failed` (state `unknown`; sessions and blocks stay; `marker-unexplained` is never cleared by a failed read).
   - Tests: echo, delayed answer with wrong length, 03→05→02, malformed 03, link loss, 1/N transition.
4. **Device identity and trust levels.** The probe result carries the identity:
   - `Info` with a **known** build ID (catalog) → trusted MAINT 1.1: full maintenance rules.
   - `Info` with an **unknown** build ID → shown read-only („Unbekannter Wartungs-Build x.y, Build-ID …“; never a known name). Stored as master state `maint-unknown`. `start`/`stop`, a marker session, bus write actions and the normal master-flash path are **refused** (`unknown-maint-build`); `stop` is never sent to such a build.
   - **Recovery from an unknown build** (the only way to flash a known image onto it), a row of its own in the master-flash table:
     - The user sets DIP 5–8 of the master OFF physically and confirms it. An open **marker session** of this installation is converted into a DIP session by this confirmation (stored with the time; `stop` is never sent).
     - Required fresh checks of the DIP path: 2 s bus quiet and `0x47` from address 0 on the pack bus, inverter confirmation, the master application answers `0x51`/`0x47` (the normal flash preflight), and the explicit confirmation „Unbekannten Wartungs-Build überschreiben“.
     - **Own master block exception:** an open `master-unclear` or `update-unclear` block **of address 0 of this installation** does not stop this recovery flash; any other block (other packs, `bootloader-unclear`, `update-interrupted`) and any other installation's work still does.
     - The flash writes `update-interrupted` first as always; the old master block is cleared only when the post-flash check (point 9) confirms the planned identity and state. An interrupted recovery flash stays blocked.
     - A master hanging in its bootloader (no application answer) is outside the app: isolation / lab recovery.
   - `Legacy` → MAINT 1.0 compatible (as today; shown as „MAINT-1.0-kompatibel“).
5. **Classification of `Info` (trusted builds).** From the raw word:
   - `FFFFFFFF` → patched-off (slaves from byte 13);
   - `00000000` → patched-on; without a matching session this is the existing `marker-unexplained` origin case (with „Ich habe den Marker selbst gesetzt“);
   - any other word → **new blocked state `marker-foreign`** (stored with raw word, time and build ID; bound to the installation). No „Ich habe ihn gesetzt“, no stop, no start, no automatic unlock by any later status (neither `02` nor a later `03`); the panel explains that the sector holds foreign content and needs an explicit sector/recovery decision (resolution: a separate confirmed action „Sektorinhalt geklärt“ that archives the record, like sector notes; the raw word must read `FFFFFFFF` or `00000000` at that moment). Counts as open work everywhere `marker-unexplained` does.
6. **Persisted master identity.** `master_state` gains (new table `master_identity(installation PRIMARY KEY, kind, base, patch, build_id, at)`) the last identity read from the master: kind (`maint-1.1` / `maint-unknown` / `maint-1.0-compatible` / `no-0x64` / `unknown`), versions, build ID and time. `Overview` returns it. After a failed read it is shown as stale („zuletzt …“). Strictly per installation id (picker switches never mix values).
7. **Display.** Master line in the pack bus panel: „16.06.13 MAINT 1.1“ (+ build ID in a tooltip) / „16.06 MAINT-1.0-kompatibel“ / „0x64 nicht unterstützt (16.06)“ from the persisted identity (RTN 04 does not prove an original image). The firmware view shows it as „Auf dem Master:“ separately from the selected image file („Ausgewählte Datei:“).
8. **RTN 05 on start or stop.** The action fails (no automatic retry) with „Master hat start/stop abgelehnt (RTN 05)“; open session and blocks stay visible. Then a fresh probe (point 3) decides the stored state; only a valid fresh `Info` or `Legacy` status drives it. `marker-foreign` stays blocked. No valid answer → `unknown` (never „nothing changed“).
9. **Post-flash check and `master-unclear` blocks.** The block's `expect` stores the **complete** post-condition: the existing policy expectation (`Zero` = `0/0`, `MarkerOn` = `1/0`, `ZeroOrUnexplained` = `0/0` as expected and `1/0` → `marker-unexplained`, each with the effective slave count) **plus** the expected image identity (`maint-1.1:<build id>` | `maint-1.0-compatible` | `no-0x64`).
   - planned 1.1: `Info` with the planned build ID, then the policy expectation on raw word and byte 13;
   - planned 1.0: `03 → RTN 05` **and** a valid `02`, then the policy expectation (this proves 1.0-compatible behaviour, not the exact code hash);
   - planned original: `03 → RTN 04` (= `no-0x64`; proves only that 0x64 is unsupported).
   Everything else → `master-unclear`; the `ZeroOrUnexplained` alternative still yields `marker-unexplained`. **One pure decision function** is used for the immediate check, the later master check (`resolved_master_blocks` / `clears_master_unclear`) and `maint_clear_block(…, "answered")`; RTN 05 where 1.1 is expected, another build ID, `0/N`/`1/N` where `0/0`/`1/0` is expected, or a failed read leave the block open. Old blocks without an image keep today's rule. Tests: `0/N`, `1/N`, `0/0`, `1/0` for each target build.
10. **Freshness and single-pack proof.** Where a fresh `1/0` or `0/0` is required, a trusted 1.1 uses the raw word (`00000000`/`FFFFFFFF`) and byte 13; 1.0 as today; an unknown build is refused (point 4).
11. **Help** (`tools/gen_help.py`): 1.0 vs 1.1, what the device reports, the new blocked states. Generic, no own values.

## Out of scope

- Writing 0x64/03 or any new firmware command; foreign marker content is not produced on purpose (not tested on hardware; its handling stays derived from code).
- Installation recognition by serial number (next design).

## Answers to the r1 questions (adopted)

1. `03` first, `02` only after RTN 05: yes for the three measured images; a missing or malformed `03` stays unknown (point 3), identity conditions for planned builds (point 9).
2. Unknown build ID: read-only, all marker commands and write actions refused (point 4).
3. RTN 05 on start/stop: failure without retry, fresh valid status only, foreign word stays blocked, no answer = unknown (point 8).
