---
title: Patched firmware: release bits
short: Bits 0, 2 and 3 in function switch 0 release or lock single access ways of patched firmware; with the pack cutoff (EMU1101-EXT Full) bit 4 (extended off) and bit 5 (lock state) join them. Which ways each bit governs is listed on this page.
related: topic.firmwareProfile, topic.switches, topic.paramWrite, topic.access
---
- **Bit 0, write release:** it governs “Write parameters and switches” and “Set the hard stop at a recharge pause” via the CAN socket. 1 allows these ways, 0 locks them; the pack then takes nothing over them (reading goes on). When it is off the app does not even send and shows “Writing locked” in the column. If you switch it off over one of these ways yourself, the app explains the way back first: unlock only via the RS485-1/2 bus (in a bank with the master halted, or a single pack) or on the display.
- **Bit 2, maintenance start:** it governs “Start maintenance” via the CAN socket (“Halt master”). 1 allows it, 0 refuses it; “Release master” does not depend on it. On a slave it is only stored and acts once the board becomes master 0. It cannot be changed via the CAN socket (the pack would refuse the whole write); the app shows it locked there. Changeable via the RS485-1/2 bus or on the display.
- **Bit 3, power/RTC:** it governs “Set clock”, “On/off”, “Set pack lock (addressed off)”, “Release pack lock (addressed on)” and “Restart” via the CAN socket; what is not listed here does not depend on bit 3. It acts only in builds whose version query (64/03) reports image flag bit 1. From EMU1101-EXT, 1 allows these ways together and 0 locks them (“Release of …”); only the first MAINT 1.6, supported for now, works the other way round: 1 locks, 0 allows (“Lock of …”). Like bit 2 it cannot be changed via the CAN socket, only via the RS485-1/2 bus or on the display. Whether a pack has this build the app knows only from its version query via the CAN socket; via the RS485-1/2 bus a note says the bit acts only in such builds. A build without the service shows the bit as without function. With the service the app offers these ways (Control, BMS clock); if the bit locks in the last state read these buttons stay off, and before every command the app reads it fresh.
- **Bit 4, extended off:** it governs “Set pack lock (addressed off)” via the RS485-1/2 bus or the CAN socket. It acts only in builds whose version query reports patch 1.6 and image flag bit 2; with Light the app does not interpret bits 4 and 5. At 0 (“off”) a direct off stays the soft off as before. At 1 (“on”) the extended off is on: then switching this pack off directly blocks the charge and discharge path including current limiter and pre-charge and stores the lock; it survives restarts and power loss, the master's on broadcasts and parameter imports do not release it. The old value FF switches it on. A normal parameter: changeable via the RS485-1/2 bus, via the CAN socket only when the pack proved the pack cutoff on this connection and writing is allowed there (bit 0); bit 3 is not needed for it.
- **Bit 5, no individual pack cutoff:** status only. “On” (1): no lock stored; “off” (0): a lock is stored. Switching off directly sets it, switching on directly releases it, also when bit 4 is at 0 meanwhile; setting bit 4 to 0 alone does not release it. The app writes bit 5 on no way: every write block, also a file, a “previous state” or a restore after a refusal, carries the state of the fresh read. If the lock state changed since the column was read, the app writes nothing and reports “Lock state changed”. A proven column with a stored lock shows “Pack cutoff active” in its header. With a pack without the cutoff (such as Light) beside it, the rows read neutrally “Bit 0.4/0.5”, and its column shows the raw bit without interpretation.
- **Both locked on a master that polls:** then none of the ways of bit 0 and bit 2 works any more. For RS485-1/2 release the bus by hand (DIP 5–8 on site) or use the display.
- **When the app interprets the bits:** only with a proof for exactly this pack: for the master its firmware identity on this connection; for a slave an entry for its board (BMS serial number), which the app creates after its own flash with a patched image or which you set with “Confirm patched firmware”. Every new flash of this pack by the app removes the proof. A flash outside the app cannot be seen: then remove the proof with “take back”.
- **Without proof:** the bits read “meaning only with proven patched firmware”, and a write via the CAN socket keeps them as the pack has them. If a pack still refuses with E3, writing was locked there: nothing taken, read the state again. When proven and unproven columns stand side by side, the rows read neutrally “Bit 0.0” and “Bit 0.2”; the tooltip in the proven columns shows the meaning. A stored state or a file without a proof does not make the rows neutral: that column shows the bits raw as 0/1.
- **Updating to patched firmware:** the flash takes the existing bits over unchanged. Older values with bit 0 or 2 at 0 lock afterwards. With EMU1101-EXT bit 3 at 1 (such as the old value FF) allows the ways named for bit 3 above, with the first 1.6 FF locks them. With an image with the pack cutoff, FF switches the extended off on; a bit 5 at 0 counts for the image as an existing lock and stays until switching on directly releases it. The firmware view shows the state beforehand (freshly read, else the last stored one with its date, unchecked).
- **Direction of bit 3 per pack:** how the app knows the direction: from the pack's identity (64/03) on this connection (image flag bit 3 as with EMU1101-EXT: 1 allows; without that flag, as on the first MAINT 1.6: 0 allows) or its stored patch proof (counts as EMU1101-EXT). Without either it reads bit 3 as without the flag. In a table with both kinds the row is named neutrally and the meaning shows per column.
