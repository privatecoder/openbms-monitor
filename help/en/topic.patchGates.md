---
title: Patched firmware: release bits
short: Bits in function switch 0 govern what works via the CAN socket: writing (bit 0), the master's maintenance start (bit 2) and, in builds with on/off and the clock, their lock (bit 3); with the pack cutoff (MAINT 1.6) the extended off (bit 4) and the lock state (bit 5) join them.
related: topic.firmwareProfile, topic.switches, topic.paramWrite
---
- **Bit 0, writing via the CAN socket:** 1 allows it, 0 locks it; the pack then takes nothing via the CAN socket (reading goes on). When it is off the app does not even send and shows “Writing locked” in the column. If you switch it off via the CAN socket yourself, the app explains the way back first: unlock only via the RS485-1/2 bus (in a bank with the master halted, or a single pack) or on the display.
- **Bit 2, maintenance start:** 1 allows “Halt master” via the CAN socket, 0 refuses it; “Release master” always works. On a slave it is only stored and acts once the board becomes master 0. It cannot be changed via the CAN socket (the pack would refuse the whole write); the app shows it locked there. Changeable via the RS485-1/2 bus or on the display.
- **Bit 3, lock of on/off, restart and clock:** only in builds whose version query (64/03) reports image flag bit 1. 1 locks on/off, restart and setting the clock via the CAN socket together, 0 allows them; reading the clock, parameters, serial numbers and the version query always work. Like bit 2 it cannot be changed via the CAN socket, only via the RS485-1/2 bus or on the display. Whether a pack has this build the app knows only from its version query via the CAN socket; via the RS485-1/2 bus a note says the bit acts only in such builds. A build without the service shows the bit as without function. With the service the app offers restart, on/off (Control) and the BMS clock via the CAN socket; with the bit at 1 in the last state read these buttons stay off, and before every command the app reads it fresh.
- **Bit 4, lock of the extended off:** only in builds whose version query reports patch 1.6 and image flag bit 2 (flags 06, with hard stop 07); with 1.5 the app does not interpret bits 4 and 5. Like every switch it reads “on” at 1: then the extended off is locked, a direct off stays the soft off as before. At 0 (“off”) the extended off is free: then switching this pack off directly via the RS485-1/2 bus or the CAN socket blocks the charge and discharge path including current limiter and pre-charge and stores the lock; it survives restarts and power loss, the master's on broadcasts and parameter imports do not release it. The old value FF reads “on” here. A normal parameter: changeable via the RS485-1/2 bus, via the CAN socket only when the pack proved the pack cutoff on this connection and writing is allowed there (bit 0); bit 3 is not needed for it.
- **Bit 5, no individual pack cutoff:** status only. “On” (1): no lock stored; “off” (0): a lock is stored. Switching off directly sets it, switching on directly releases it, also when bit 4 is back at 1 meanwhile; setting bit 4 to 1 alone does not release it. The app writes bit 5 on no way: every write block, also a file, a “previous state” or a restore after a refusal, carries the state of the fresh read. If the lock state changed since the column was read, the app writes nothing and reports “Lock state changed”. A proven column with a stored lock shows “Pack cutoff active” in its header. With a pack without the cutoff (such as 1.5) beside it, the rows read neutrally “Bit 0.4/0.5”, and its column shows the raw bit without interpretation.
- **Both locked on a master that polls:** then the CAN socket no longer helps. For RS485-1/2 release the bus by hand (DIP 5–8 on site) or use the display.
- **When the app interprets the bits:** only with a proof for exactly this pack: for the master its firmware identity on this connection; for a slave an entry for its board (BMS serial number), which the app creates after its own flash with a patched image or which you set with “Confirm patched firmware”. Every new flash of this pack by the app removes the proof. A flash outside the app cannot be seen: then remove the proof with “take back”.
- **Without proof:** the bits read “meaning only with proven patched firmware”, and a write via the CAN socket keeps them as the pack has them. If a pack still refuses with E3, writing was locked there: nothing taken, read the state again. When proven and unproven columns stand side by side, the rows read neutrally “Bit 0.0” and “Bit 0.2”; the tooltip in the proven columns shows the meaning. A stored state or a file without a proof does not make the rows neutral: that column shows the bits raw as 0/1.
- **Updating to patched firmware:** the flash takes the existing bits over unchanged. Older values with bit 0 or 2 at 0 lock afterwards, bit 3 at 1 (such as the old value FF) locks on/off and setting the clock. With an image with the pack cutoff, FF leaves the extended off off; a bit 5 at 0 counts for the image as an existing lock and stays until switching on directly releases it. The firmware view shows the state beforehand (freshly read, else the last stored one with its date, unchecked).
