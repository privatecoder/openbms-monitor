---
title: Connection
short: How the app connects to the batteries: via a USB-RS485 adapter or an RS485-to-Ethernet gateway (TCP).
related: topic.buses
---
- **Installation:** before connecting you choose the installation at the top. Everything the app stores (recording, serial numbers, parameter states, cell types, groups) then belongs to it. A USB port never changes the choice, since the same adapter moves between banks. A gateway that belongs to exactly one active installation chooses it by itself; if it belongs to several, the chosen one stays when it is among them, otherwise the app asks you to choose. If the installation has no port for the chosen bus yet, the connected one is linked when connecting (one line, no dialog); a connection at the CAN socket never becomes the endpoint for the RS485-1/2 bus. If it has another one, a line below the status asks “Save as the endpoint for the RS485-1/2 bus of “A”?” or “Save as the endpoint for the CAN socket (RS485) of “A”?” with “Save” and “No”; without “Save” the stored one stays, and after “No” the app does not ask again in this session. Choosing the installation or the bus fills network/USB and address or port from the installation's ports (see Installations): CAN socket or RS485-1/2. The last connection with the installation gives bus and pack count, its address only where nothing is stored for that bus; if both are empty, the USB field stays empty so that no port of another installation remains. An edit of the address field holds until the bus or the installation changes next. While connected the choice and the connection fields (network/USB, address or port, bus, packs) are fixed; to change them, disconnect first. The automatic reconnect uses them too.
- **View only:** for a quick look at a foreign bank. Nothing is stored (no recording, no serial numbers, no parameter states) and nothing is written to the packs.
- **Right bank:** after connecting the app reads the serial numbers and compares each pack's BMS serial number (String 2) with the chosen installation. New or moved boards are named in a line with “Yes, take over”; a board of another installation in a red line with “Disconnect” and “Connect with “B”” (disconnects, chooses B and connects again). On the RS485-1/2 bus recording (and linking a new endpoint to the installation) starts only once the serial numbers confirm the bank: a pack the installation knows, packs without a serial number, or all reads ended without a result. If the installation knows none of the packs, it starts only after “Yes, take over”. Until then it says “Recording waits for the installation check”; on the CAN socket String 2 is not visible, there the app only compares the master's battery serial number and keeps recording. Packs without a serial number cannot be assigned (see Installations).
- **Network (TCP):** gateway address as `host:port`, e.g. `192.168.1.10:4196`. The baud rate is configured on the gateway (CAN socket 9600, RS485-1/2 bus 19200).
- **USB/serial:** select the adapter's port; the baud rate follows the selected bus.
- **Check when connecting:** “Connect” first asks addresses 0–15 with 0x51 (the ones to be polled first) and counts as connected only when a pack answers; on the CAN socket the master's Modbus answer is enough. If nothing answers, the app stays disconnected and says what it heard: nothing, unreadable data (usually a wrong baud rate) or a master polling its slaves. On a USB port it then tries the other bus's baud rate; if a pack answers there, “Connect via …” switches with one click. A gateway has its baud rate set, so the app names what to check. A pack in its bootloader or shortly after a restart (about 5 s) does not answer either. An endpoint where nothing answers is not linked to an installation and not recorded.
- **Order after connecting:** on the CAN socket the app first reads the master's system values (Modbus) and shows them at once. If the master reports its slave count (only with the maintenance firmware, command 0x64), the app polls exactly these packs without a search. Otherwise the **Packs** setting applies: “search” scans addresses 0–15, “count n” starts polling addresses 0 to n−1 at once, “fixed address k” polls exactly one pack at address k without a search (such as a single board at DIP address 1). If with “count n” any expected address is missing, or the fixed address does not answer, the app searches after all (0–15) and says so in the connection line. The expected addresses stay polled (a pack silent right now shows “without a current answer”, and its return is noticed), packs found outside them join. Then all packs are polled every 2 s; names and firmware versions follow shortly after the start. While the master's maintenance mode is active it reports 0 slaves; then the app searches.
- Without a valid answer for **60 s**, the connection counts as lost (“Connection lost”). If the gateway closes the connection or it fails with an error, it counts as lost at once. The app then reconnects automatically, also with the window hidden: after 1, 2, 4, 8 and 16 minutes, then every 30 minutes, ten times in all (about 3 hours). Then it gives up; “Connect” starts again by hand.
- If a single pack stops answering, or only its status (0x44) does, the app keeps the last values but no longer counts them: sums, extremes and groups come only from current answers (at most two polling rounds old), and the pack row shows “no current data (X s ago)” or “status old” instead of an absence of alarms; the head says how many packs have no current status (never read or old); “No messages” shows only when every counted pack has a current status. In the pack view old values stay visible, but faded and marked old; state, balancing and the cells' balancer marks come only from a current status, without one it says “status unknown”. The datasheet check does not rate old values. On the CAN socket, charge and discharge limits without a current system value count as unknown (“system values old”). If the adapter echoes the app's own requests, the app skips those lines; an answer whose layout does not fit the request (such as a late 0x42 answer while 0x44 waits) is discarded and the app waits for the right one.
- Only one program may poll the bus at a time. If e.g. the Home Assistant add-on uses the same gateway, requests collide; then take the data via **Home Assistant (MQTT)** (see there) or stop the add-on first.
